# Agent Prompt: Onboard a New Project to the Agent-Context Store

Use this prompt to instruct an agent to set up a new project with the agent-context
workflow: instructions, memory, docs and behavior entities in the store, and on disk
only what a harness loader reads.

> **Disk layer:** `.agents/` and `.claude/` in a repo are generated by
> `project-materialize.py` from store entities and are never an authoring location
> (`get_doc("agents-layout.md")`). Stack templates and `init-project.py` /
> `sync-project-config.py`: `get_doc("project-workflow-architecture.md")`.

---

## The Prompt

```
You are onboarding a new project into the agent-context store. The goal: all
instructions, memory, documentation, skills, commands, scripts, hooks and agent
definitions live in ~/.agent-context and are written through the agent-context MCP
server. The files under `.agents/` and `.claude/` in the repo are generated from
those entities. Do not author them by hand.

## Context

The agent-context MCP server is connected. Call `get_session_context` with the
project's working directory to check whether the project already exists. If it does,
you are updating; if not, you are creating it.

## Step 1: Register the project

```
upsert_project(
  canonical_remote="<git remote URL>",
  display_name="<short name>",
  stack="<csharp-dotnet|nextjs|kotlin-android|python|etc>",
  integration_branch="<dev|main|development>",
  local_path="<absolute path>",
  workspace="<workspace name>"
)
```

## Step 2: Create the project instruction

Write one `always`-loaded instruction block that covers:

- **What the project is** (1-2 sentences: stack, solution file, deploy target)
- **Critical rules** (what must not be violated, for example legacy API
  preservation or DateTime rules)
- **Conventions** (time handling, logging, commit message style)
- **Patterns** (architectural invariants: data access, caching rules, build
  constraints)
- **Build & Test** (the commands to run, and what is forbidden, such as running all
  tests)
- **Worktree workflow** (integration branch, remote name, create and finish
  commands, project-specific gate steps)
- **Pointers** (how to find architecture docs, feature docs and style guides, all
  as `get_doc()` / `list_entities("doc", …)` calls, never filesystem paths)
- **Task tracking**: omit this. There is no tracker; open items are raised with user
  in conversation. Do not invent a per-project task system.

Use `upsert_instruction(title, body, project="<name>")`.

Do not duplicate rules that already exist in the global instruction. Reference
them ("see the global instruction's *Worktrees* and *Filesystem and git safety*
sections").

## Step 3: Create the CLAUDE.md bootstrap file

Write a minimal CLAUDE.md at the project root (5 lines max):

```markdown
# <Project Name>

<Stack>. All instructions, memory, and documentation are in the
agent-context store. Call `get_session_context` with this working directory on your
first turn: it returns everything needed for the session.
```

This is the only documentation file that lives in the repo. It is the bootstrap
pointer for agents that read CLAUDE.md before MCP tools are available.

## Step 4: Write feature and architecture documentation

For each major subsystem or feature, create a doc in the store:

```
upsert_doc(
  path="features/<feature-name>.md",
  title="<Feature Title>",
  body="<feature documentation>",
  project="<name>"
)
```

Also create:
- `architecture.md`: project structure, tiers, config layers, deploy mechanics
- Any workflow docs (for example `worktrees.md` for project-specific overrides)

These are lazy-loaded: agents fetch them when working in a relevant area.

## Step 5: Store skills, commands, scripts, hooks, agent definitions

Create each one as a store entity. The materializer writes the files; do not write
them under `.agents/` or `.claude/` yourself.

- Skills (deploy workflows, verification, audits):
  `upsert_skill(name, description, body, project="<name>")`
- Commands (slash commands):
  `upsert_command(name, body, description, project="<name>")`
- Scripts (bash or python run directly):
  `upsert_script(name, script_body, language="sh", description, project="<name>")`
- Hooks (PostToolUse formatters and the like):
  `upsert_hook(name, event_type, script_body, matcher, language="sh", project="<name>")`
- Agent definitions (custom subagent types):
  `upsert_agent_definition(name, description, body, project="<name>")`

A skill or command shared by a family of repos goes at workspace scope
(`workspace="<name>"`) and reaches every project in that workspace.

## Step 6: Materialize

```
python3 ~/.agent-context/global/scripts/project-materialize.py <repo>
```

This writes the entities to `<repo>/.agents/` and rebuilds the `.claude/`
projection through `agents-materialize.py`. It is safe to re-run and also runs at
session start, so a fresh clone on another device needs no separate step.
`project-materialize.py --check <repo>` reports drift and writes nothing (exit 3
means drift).

## Step 7: Configure settings.json

Harness settings live at `.agents/claude/settings.json` and
`.agents/claude/settings.local.json`; `agents-materialize.py` hardlinks both into
`.claude/`. Where a stack template exists, `init-project.py` scaffolds them
(`get_doc("project-workflow-architecture.md")`). With no template, write them
directly:

- `settings.json`: project hooks (PostToolUse formatters, SessionStart sweepers),
  which run in place from `.agents/hooks/`, and any plugins the project needs.
  `worktree.baseRef` is managed fleet-wide by `home-settings-sync.py`.
- `settings.local.json`: `permissions.allow` (MCP tool allowlists, WebFetch
  domains, Skill permissions) and other machine-specific permissions.

No memory-redirect file is needed: memory is store-only. Do not write anything
under `~/.claude/projects/.../memory/`.

## Step 8: Clean up any existing filesystem documentation

If the project previously had docs in `.agents/docs/`, delete them: the store is
the authority. A command's shell block that needs a doc's text fetches it with
`python3 "$HOME/.agent-context/global/scripts/store-doc.py" --project <P> <doc-path>`.
Keep only files that command scripts consume with `awk` or `cat` (templates).

## Step 9: Verify

Run `get_session_context` and confirm:
- Project identity loads correctly
- Instructions load (global + workspace + project)
- Memory index shows any migrated memories
- No open audit observations from the setup

Run `project-materialize.py --check <repo>` and confirm it reports no drift.

## What is on the filesystem

| Path | Source |
|------|--------|
| `CLAUDE.md` | Hand-written bootstrap pointer (read before MCP is available) |
| `.agents/claude/settings.json`, `settings.local.json` | Template or hand-written; hardlinked into `.claude/` |
| `.agents/claude/{skills,commands,agents}/` | Generated from store entities; copied into `.claude/` |
| `.agents/{scripts,hooks}/` | Generated from store entities; run in place |
| `.claude/` | Generated projection; never edited |

## What never goes on the filesystem

- Feature documentation (use `upsert_doc`)
- Architecture docs (use `upsert_doc`)
- Memory and feedback (use `upsert_memory`)
- Workflow runbooks (use `upsert_doc`)
- Iteration reports, audit logs, analysis files
```

---

Use this prompt as written, or adapt the stack-specific parts (build commands,
formatter hooks, test patterns) to the target project's technology.

---

## Multi-machine note

`local_path` registered via `upsert_project` is tied to the current machine, but
no per-machine path setup is required: project resolution is by git remote
(`resolve_project(cwd)` matches the cwd's git remote to a project's
`canonical_remote`), so the same store resolves correctly on every machine.
Clone a repo whose remote matches a known project and it resolves. All store
content is global (visible on all machines); per-machine pinning does not exist.
See the *Machine scoping* section of `get_doc("store-operations.md")`.
